# 支付宝沙箱 App 支付接入设计（Liji Tea App）

- 日期：2026-03-23
- 项目：liji-tea-app
- 目标平台：Android
- 当前阶段：设计评审稿
- 设计范围：支付宝沙箱 App 支付真接入
- 推荐方案：Expo Development Build + Android 原生支付宝 SDK 桥接 + 服务端下单与回调验签

---

## 1. 背景

当前项目是 Expo 应用，Android 包名已配置为：

- `com.liji.teaapp`

项目当前支付流程仍是前端模拟流程：

- 支付页在客户端直接推进“处理中 / 成功”状态
- 客户端直接调用订单状态更新逻辑，将订单改为 `paid`

这套逻辑只适合演示，不满足真实支付要求。  
如果要接入支付宝沙箱并跑通真实链路，必须补齐以下能力：

- 服务端生成支付订单串
- 客户端调用支付宝 Android SDK 发起支付
- 服务端接收支付宝异步通知并验签
- 仅服务端在验签通过后更新订单状态

---

## 2. 设计目标

本次设计的目标如下：

1. 在 Android App 中接入支付宝沙箱 App 支付。
2. 保留当前 Expo 项目结构，不整体迁移到纯原生工程。
3. 通过服务端生成 `orderString`，避免私钥出现在客户端。
4. 通过服务端异步通知验签，确保订单状态可信。
5. 替换当前前端模拟支付逻辑，形成真实支付闭环。

---

## 3. 非目标

本次设计不包含以下内容：

- 微信支付接入
- iOS 支付接入
- 正式环境商户切换方案的完整上线流程
- 营销券、拆单、退款、对账等扩展能力
- 支付失败后的自动补偿系统

---

## 4. 当前现状

### 4.1 项目形态

当前仓库是 Expo Managed 形态，关键特征如下：

- 使用 `expo`
- 使用 `expo-router`
- 当前没有原生 `android/` 工程目录
- 当前支付页逻辑仍为前端模拟

### 4.2 当前支付问题

现有实现的核心问题：

1. 订单金额和支付结果由客户端驱动。
2. 客户端可直接将订单状态改成 `paid`。
3. 没有服务端签名、验签和回调处理。
4. 没有真实支付宝 SDK 调用链路。

这意味着当前实现无法作为真实支付方案继续演进，必须替换。

---

## 5. 方案选型

### 5.1 方案 A：保留 Expo，切到 Development Build

做法：

- 保留现有 Expo Router 架构
- 增加自定义原生模块或原生桥接
- 用 `expo prebuild` 或 config plugin 引入支付宝 Android SDK
- 服务端新增创建支付订单和异步通知处理

优点：

- 对现有项目改动最小
- 可以保留现有页面、路由和状态管理结构
- 能满足支付宝 App 支付对 Android 原生 SDK 的依赖

缺点：

- 不能继续只靠 Expo Go 调试支付
- 需要处理原生桥接层
- 需要补服务端闭环

### 5.2 方案 B：整体转 Bare React Native / 原生 Android 工程

优点：

- 原生能力最直接
- 接第三方支付 SDK 更顺手

缺点：

- 工程维护成本明显上升
- 偏离当前仓库结构
- 对当前目标来说改动过重

### 5.3 方案 C：继续沿用前端模拟支付，只做界面演示

优点：

- 实现最快

缺点：

- 不具备真实支付能力
- 无法验证签名、回调和订单闭环
- 不符合上线前的正确技术路径

### 5.4 结论

推荐采用 **方案 A：Expo Development Build + 原生桥接 + 服务端支付闭环**。

这是当前项目下成本最低、正确性最高的方案。

## 6. 总体架构

整体架构分为 4 个模块：

1. 客户端支付页
2. 服务端下单接口
3. Android 原生支付宝 SDK 桥接层
4. 服务端支付回调与验签处理

### 6.1 架构图

```text
[App 结算页]
      |
      v
[客户端支付页]
      |
      | 1. 请求创建支付宝订单
      v
[服务端 create-order]
      |
      | 2. 调用 alipay.trade.app.pay
      v
[支付宝沙箱网关]
      |
      | 3. 返回 orderString
      v
[客户端原生桥接层]
      |
      | 4. 调起支付宝 Android SDK
      v
[支付宝沙箱钱包]
      |
      | 5. 用户完成支付
      v
[支付宝异步通知 notify]
      |
      | 6. 服务端验签 + 更新订单状态
      v
[订单状态表]
      |
      | 7. 客户端查询结果
      v
[支付结果页]
```

## 7. 模块职责划分

### 7.1 客户端支付页

职责：

- 发起“创建支付订单”请求
- 接收服务端返回的 `orderString`
- 调用原生桥接层发起支付宝支付
- 展示支付中、支付成功、支付失败 UI
- 轮询或查询服务端订单状态

不负责：

- 计算最终支付金额
- 使用私钥签名
- 直接把订单改为 `paid`

### 7.2 服务端下单接口

职责：

- 校验用户身份和订单归属
- 校验订单当前状态是否允许支付
- 重新计算订单金额
- 调用支付宝开放平台 `alipay.trade.app.pay`
- 返回 `orderString`

### 7.3 原生桥接层

职责：

- 接收 JS 层传入的 `orderString`
- 调用支付宝 Android SDK
- 将支付结果回传给 JS 层

### 7.4 服务端回调接口

职责：

- 接收支付宝异步通知
- 验证支付宝签名
- 校验金额、商户订单号、应用 ID、交易状态
- 验签成功后更新订单状态为 `paid`
- 记录回调内容和支付流水

## 8. 支付流程设计

### 8.1 下单前提

用户在结算页完成以下数据选择：

- 收货地址
- 商品
- 数量
- 配送方式
- 支付方式为 `alipay`

客户端提交的最小必要信息应为：

- `orderId`
- 用户身份令牌
- 支付渠道：`alipay`

客户端不再提交最终可信金额。

### 8.2 创建支付订单流程

1. 客户端进入支付页。
2. 客户端调用服务端 `create-order`。
3. 服务端读取订单明细和商品价格。
4. 服务端重新计算应付金额。
5. 服务端调用支付宝沙箱 `alipay.trade.app.pay`。
6. 服务端返回 `orderString`。
7. 客户端调用原生支付宝 SDK。

### 8.3 客户端支付结果处理

支付宝 SDK 返回结果后：

- 客户端只将其视为“支付发起结果”或“客户端观察结果”
- 不直接作为最终支付成功依据
- 客户端进入“等待确认”状态
- 通过查询订单状态确认是否最终成功

### 8.4 服务端异步通知流程

1. 支付宝通知服务端 `notify`。
2. 服务端使用支付宝公钥验签。
3. 校验以下字段：
   - `out_trade_no`
   - `trade_no`
   - `total_amount`
   - `app_id`
   - `seller_id`
   - `trade_status`
4. 验证通过后，将订单状态更新为 `paid`。
5. 写入支付流水和回调日志。
6. 返回支付宝要求的成功响应。

### 8.5 客户端最终状态确认

客户端可采用两种方式：

- 轮询订单状态接口
- 进入支付结果页时主动刷新订单详情

推荐先用“短轮询 + 页面刷新”的简单方案。

## 9. 服务端接口设计

### 9.1 创建支付宝订单

接口建议：

- `POST /api/payments/alipay/create-order`

请求体示例：

```json
{
  "orderId": "order_xxx"
}
```

响应体示例：

```json
{
  "orderString": "app_id=xxx&biz_content=...&sign=...",
  "outTradeNo": "ALI202603230001",
  "amount": "88.00"
}
```

服务端处理规则：

1. 校验登录态。
2. 校验订单属于当前用户。
3. 校验订单状态为 `pending_payment`。
4. 根据服务端订单明细重新计算金额。
5. 生成唯一 `out_trade_no`。
6. 调用 `alipay.trade.app.pay`。
7. 返回签名后的 `orderString`。

### 9.2 查询支付状态

接口建议：

- `GET /api/payments/orders/{orderId}/status`

响应体示例：

```json
{
  "orderId": "order_xxx",
  "status": "paid",
  "paymentStatus": "success",
  "tradeNo": "20260323xxxxxx"
}
```

### 9.3 支付宝异步通知

接口建议：

- `POST /api/payments/alipay/notify`

要求：

- 不需要客户端 token
- 必须做签名校验
- 必须幂等处理
- 只允许合法状态迁移

## 10. 数据模型调整建议

建议在订单表和支付表中补充以下字段。

### 10.1 订单表建议字段

新增或确认以下字段：

- `payment_channel`
- `payment_status`
- `out_trade_no`
- `paid_amount`
- `paid_at`
- `trade_no`
- `payment_error_code`
- `payment_error_message`

状态建议：

- `pending_payment`
- `paying`
- `paid`
- `payment_failed`
- `closed`

### 10.2 支付流水表

建议新增独立支付流水表，例如 `payment_transactions`：

字段建议：

- `id`
- `order_id`
- `user_id`
- `channel`
- `out_trade_no`
- `trade_no`
- `amount`
- `status`
- `request_payload`
- `notify_payload`
- `notify_verified`
- `created_at`
- `updated_at`

这样可以避免订单表过载，也方便后续排查问题。

## 11. 客户端改造设计

### 11.1 支付页状态机

建议将支付页状态从当前模拟流程改为：

- `idle`
- `creating_order`
- `invoking_sdk`
- `waiting_confirm`
- `success`
- `failed`

### 11.2 建议交互流程

1. 用户点击“确认支付”。
2. 页面进入 `creating_order`。
3. 请求服务端创建订单。
4. 成功后进入 `invoking_sdk`。
5. 调用原生桥接层发起支付宝支付。
6. SDK 返回后进入 `waiting_confirm`。
7. 轮询订单状态。
8. 若服务端确认已支付，则进入 `success`。
9. 若超时或失败，则进入 `failed`。

### 11.3 当前页面必须移除的逻辑

必须删除以下错误做法：

- 客户端直接将订单状态改为 `paid`
- 用固定延时模拟支付成功
- 以客户端本地参数作为可信支付金额

## 12. Expo 与原生集成设计

### 12.1 为什么不能只用 Expo Go

支付宝 App 支付依赖 Android 原生 SDK。  
Expo Go 不支持任意自定义原生模块，因此不能仅靠 Expo Go 完成支付接入。

### 12.2 推荐集成方式

推荐使用：

- `expo-dev-client`
- `expo prebuild`
- Android 原生模块桥接
- 必要时增加 config plugin 处理 SDK 引入和配置

### 12.3 原生桥接层能力

JS 层建议只暴露一个最小接口：

```ts
pay(orderString: string): Promise<{
  resultStatus: string;
  memo?: string;
  result?: string;
}>
```

返回值说明：

- `resultStatus`：支付宝 SDK 返回状态码
- `memo`：附加说明
- `result`：原始结果串

注意：

- JS 层不能根据 `resultStatus === 9000` 直接把订单视为最终支付成功
- 最终成功仍以服务端验签后的订单状态为准

## 14. 安全要求

### 14.1 必须满足

1. 私钥仅保存在服务端。
2. 客户端不得参与金额签名。
3. 服务端必须重新计算应付金额。
4. 服务端必须校验订单归属。
5. 服务端异步通知必须验签。
6. 支付状态更新必须幂等。
7. 订单状态迁移必须受限。
8. 客户端支付结果只能做展示参考。

### 14.2 不允许的实现

以下做法禁止继续保留：

- 客户端直接改订单为 `paid`
- 客户端自己计算最终可信金额
- 客户端保存支付宝私钥
- 只依赖客户端 SDK 返回值判定最终支付成功

## 15. 错误处理设计

### 15.1 创建订单失败

场景：

- 订单不存在
- 订单不属于当前用户
- 订单已支付
- 支付宝下单失败
- 服务端配置错误

处理方式：

- 前端提示“创建支付订单失败”
- 保留重试入口
- 服务端记录错误上下文

### 15.2 SDK 调起失败

场景：

- 设备未安装支付宝
- 原生桥接异常
- SDK 调用失败

处理方式：

- 前端展示明确失败原因
- 允许用户重新发起支付
- 不改订单状态

### 15.3 异步通知失败

场景：

- 验签失败
- 金额校验失败
- 回调重复
- 数据库更新失败

处理方式：

- 服务端完整记录日志
- 幂等重试
- 对异常订单保留人工排查入口

## 16. 测试方案

### 16.1 联调前检查

1. 支付宝开放平台已配置 Android 包名与应用签名。
2. 沙箱 `appid`、私钥、公钥、网关可用。
3. 沙箱钱包安装完成。
4. 服务端 `notify_url` 可被支付宝访问。
5. Android development build 能正常安装运行。

### 16.2 测试用例

#### 正常支付

- 创建订单成功
- 成功拉起支付宝沙箱钱包
- 支付完成后收到异步通知
- 订单状态从 `pending_payment` 变成 `paid`

#### 异常支付

- 用户取消支付
- 支付失败
- SDK 未安装
- 回调签名错误
- 金额不匹配
- 重复回调

### 16.3 验收标准

达到以下条件才算沙箱接入完成：

1. App 内可成功拉起支付宝沙箱钱包。
2. 支付订单由服务端生成。
3. 客户端不再直接写 `paid`。
4. 服务端异步通知验签通过后更新订单。
5. 客户端最终成功页来自服务端确认结果。
6. 重复通知不会导致重复入账。

## 18. 风险与约束

### 18.1 关键风险

1. Expo 原生桥接集成成本高于纯 JS 接入。
2. 支付宝异步通知需要公网可访问地址。
3. 沙箱环境与正式环境配置容易混用。
4. 当前订单模型可能不够支撑支付状态留痕。

### 18.2 应对策略

1. 优先完成服务端闭环，再接原生 SDK。
2. 接口设计先定稳定，再接前端。
3. 将支付流水与订单表拆开。
4. 环境变量严格分环境管理。

---

## 19. 最终结论

本项目要接入支付宝沙箱 App 支付，正确路径是：

- 保留 Expo 项目
- 切换到 Development Build
- 增加 Android 原生支付宝 SDK 桥接
- 服务端负责生成 `orderString`
- 服务端负责异步通知验签与订单落库
- 客户端只负责发起支付和展示状态

这也是将当前“模拟支付”升级为“真实可信支付链路”的最小可行方案。

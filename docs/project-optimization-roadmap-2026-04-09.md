# 项目优化整改路线图

生成时间：2026-04-09
关联分析文档：`docs/project-optimization-analysis-2026-04-09.md`

## 1. 目标

本路线图用于把当前项目从“功能基本齐全，但边界开始松动”的状态，推进到“关键链路更稳、配置更安全、后续更容易继续迭代”的状态。

本轮优化不追求大规模重构，重点遵循以下原则：

- **KISS**：先修最直接影响稳定性的点，不同时引入大规模新抽象。
- **YAGNI**：不为了未来假设场景提前设计复杂框架。
- **SOLID**：只在当前已经明显职责混杂的模块上做边界收口。

---

## 2. 本轮范围

### 范围内

- 支付渠道配置安全性
- 结算页与默认地址的订阅正确性
- 优惠券链路的请求收口与调用统一
- 社区分页一致性
- 关键协作层回归测试

### 暂不纳入

- 全量 UI 重构
- 社区、订单、优惠券全域状态管理重写
- 原生模块大改
- 支付宝真机链路增强
- E2E 自动化体系搭建

---

## 3. 执行顺序总览

### 第一阶段：P0 稳定性收口

目标：

- 防止错误配置直接影响支付展示与支付行为
- 防止结算页使用错误地址下单
- 防止社区 feed 出现重复数据
- 防止优惠券链路继续扩散重复调用模式

建议顺序：

1. 收紧支付渠道配置默认值
2. 修复结算页默认地址 selector
3. 统一优惠券 Edge Function 调用入口
4. 修复社区分页 merge 去重

### 第二阶段：P1 工程治理

目标：

- 收敛 store 写操作的一致性风险
- 降低大文件维护成本
- 降低第三方头像依赖带来的稳定性与隐私风险

建议顺序：

1. 地址默认值改为原子更新
2. 收藏逻辑补失败回滚
3. 拆分 `communityStore` / `tracking.tsx` / `userStore`
4. 处理社区头像 fallback

### 第三阶段：P2 测试与规范固化

目标：

- 让高风险协作层具备基本回归保护
- 让后续迭代不再重复引入同类问题

建议顺序：

1. 增加页面与 store 协作层测试
2. 统一高频数据的缓存与去重策略
3. 将关键约束沉淀成开发规范

## 4. 第一阶段详细方案

### 4.1 任务 A：收紧支付渠道配置

涉及文件：

- `src/lib/paymentConfig.ts`
- `src/components/checkout/PaymentMethods.tsx`
- `src/hooks/usePaymentScreenState.ts`
- `src/lib/paymentFlow.ts`

当前问题：

- `wechat` 和 `card` 默认启用。
- 当前所有非 `alipay` 渠道都会走 mock 支付执行器。
- 一旦环境变量漏配，测试用能力可能直接暴露给用户。

改造目标：

- mock 渠道默认关闭。
- 只有显式开启的渠道才在结算页展示。
- 生产环境不允许隐式落到 mock。

建议做法：

1. 将 `wechat` / `card` 默认值改为 `false`。
2. 在支付配置里增加“是否允许 mock 渠道”的显式判断。
3. 在支付流程入口增加保护，避免隐藏渠道仍被路由参数直接调用。

验收标准：

- 环境变量未配置时，结算页只显示明确允许的渠道。
- 非允许渠道即使通过路由参数传入，也无法触发支付流程。
- 本地开发仍能显式开启 mock 渠道完成联调。

### 4.2 任务 B：修复结算页默认地址订阅边界

涉及文件：

- `src/app/checkout.tsx`
- `src/stores/userStore.ts`

当前问题：

- `checkout.tsx` 订阅的是 `getDefaultAddress` 方法，不是默认地址结果。
- 地址变化后，页面存在不刷新的可能。

改造目标：

- 页面直接订阅默认地址结果。
- 默认地址变化后，结算页立即同步更新。

建议做法：

1. 在 `checkout.tsx` 中改为 selector 直接读取默认地址。
2. 如有必要，在 `userStore` 中补一个稳定的派生 selector。

验收标准：

- 新增地址后返回结算页能看到最新地址。
- 切换默认地址后结算页立即显示新默认地址。
- 下单提交时使用的是当前最新默认地址。

### 4.3 任务 C：统一优惠券链路的调用与缓存策略

涉及文件：

- `src/stores/couponStore.ts`
- `src/lib/supabaseFunction.ts`
- `src/app/_layout.tsx`
- `src/app/checkout.tsx`
- `src/app/coupons.tsx`

当前问题：

- 根布局、结算页、优惠券页都会重复拉取优惠券数据。
- `claimCoupon` 直接调用 `supabase.functions.invoke`，没有复用统一封装。
- store 映射层仍存在 `any`。

改造目标：

- 优惠券请求入口收敛。
- Edge Function 调用统一走共享封装。
- 重复请求减少到“必要范围”。

建议做法：

1. `claimCoupon` 改为使用 `invokeSupabaseFunctionStrict`。
2. 给公开券和用户券增加简单的 in-flight 去重或短 TTL。
3. 重新定义优惠券返回结构，尽量移除 `any`。
4. 根布局只做预热，页面层尽量复用 store 结果。

验收标准：

- 页面切换时不再出现明显重复请求。
- 优惠券领取失败、鉴权失败、业务失败都能走统一错误格式。
- 当前选中的券在刷新用户券后仍能被正确校验和清理。

### 4.4 任务 D：修复社区分页去重

涉及文件：

- `src/stores/communityStore.ts`

当前问题：

- 分页直接拼接数组，未按 `post.id` 去重。

改造目标：

- 分页、刷新、详情回写共享同一套去重逻辑。

建议做法：

1. 引入 `mergePostList` 或 `upsertPosts`。
2. `loadMore` 改为基于 `id` merge，而不是直接 `concat`。
3. 为帖子详情回写与分页结果统一状态入口。

验收标准：

- 连续加载更多不出现重复卡片。
- 刷新后再次加载更多不出现重复项。
- 详情页回写后的帖子信息不会被旧分页结果覆盖。

## 5. 第二阶段详细方案

### 5.1 地址默认值改为原子更新

涉及文件：

- `src/stores/userStore.ts`
- `supabase/migrations/*`
- 可能新增 RPC 或数据库约束

目标：

- 任何时刻一个用户只有一个默认地址。
- 地址默认值更新不依赖“两步写”。

验收标准：

- 网络抖动或重复点击不会产生多个默认地址。
- 客户端和数据库状态最终一致。

### 5.2 收藏逻辑补失败回滚

涉及文件：

- `src/stores/userStore.ts`

目标：

- 收藏按钮仍保留乐观更新体验。
- 同步失败时 UI 能回滚或至少显示错误。

验收标准：

- 断网或服务端失败时，收藏状态不会长期显示错误结果。

### 5.3 拆分大文件

优先对象：

- `src/stores/communityStore.ts`
- `src/app/tracking.tsx`
- `src/stores/userStore.ts`

建议原则：

- 先提 mapper 和纯逻辑函数。
- 再拆 query / action / state。
- 最后才拆页面展示块。

验收标准：

- 单文件职责明显变窄。
- 业务行为不变。
- 拆分后测试更容易补齐。

### 5.4 移除第三方头像 fallback 依赖

涉及文件：

- `src/stores/communityStore.ts`
- 可能新增本地占位资源

目标：

- 社区列表在弱网下更稳定。
- 避免用户昵称参数出站。

验收标准：

- 无头像用户仍能稳定展示默认头像。
- 列表不依赖第三方头像生成服务。

## 6. 第三阶段详细方案

### 6.1 补关键回归测试

建议优先补的测试：

1. 结算页默认地址切换测试
2. 支付渠道配置测试
3. 社区分页去重测试
4. 优惠券选择与失效回退测试

说明：

- 这几项测试价值高于继续新增纯工具函数测试。
- 它们更能覆盖当前最容易出问题的真实边界。

### 6.2 统一请求去重规范

建议沉淀的规范：

- 哪类数据允许根布局预热
- 哪类数据必须由页面主动刷新
- 哪类请求需要 TTL
- 哪类请求需要 in-flight 去重
- 哪类请求必须走统一 Edge Function 封装

## 7. 建议的提交拆分方式

为了降低回归风险，不建议把本轮优化一次性揉成一个大提交。建议按下面顺序拆分：

### 提交 1：支付配置收紧

- 修改支付配置默认值
- 增加 mock 保护
- 调整结算页渠道显示

### 提交 2：结算地址订阅修复

- 调整 `checkout.tsx`
- 增加默认地址 selector

### 提交 3：优惠券链路收口

- `claimCoupon` 接入统一封装
- 减少重复请求
- 补充类型守卫

### 提交 4：社区分页修复

- 引入去重 merge
- 补回归测试

### 提交 5：P1 工程治理

- 地址原子更新
- 收藏失败回滚
- 大文件拆分

---

## 8. 风险与注意事项

### 风险 1：支付渠道配置调整会影响现有联调习惯

说明：

- 一旦 mock 默认关闭，本地联调同学可能觉得“功能消失了”。

处理方式：

- 在 README 或环境变量示例里明确写清楚启用方式。

### 风险 2：结算页地址逻辑修复后可能暴露历史数据问题

说明：

- 之前如果一直在使用旧地址下单，修复后会暴露真实默认地址状态。

处理方式：

- 修复后应配合手动回归下单流程。

### 风险 3：优惠券请求收口后会改变部分页面刷新时机

说明：

- 如果页面之前隐式依赖“重复请求一定会刷新 UI”，收口后可能需要补显式刷新逻辑。

处理方式：

- 对优惠券页、结算页、登录后首次进入三条路径分别验证。

## 9. 推荐落地节奏

如果按实际开发效率考虑，推荐节奏如下：

### 第 1 天

- 完成支付配置收紧
- 完成结算地址订阅修复

### 第 2 天

- 完成优惠券链路收口
- 完成社区分页去重修复

### 第 3 天

- 补 P0 相关回归测试
- 做一次集中回归

### 第 4 天及以后

- 再进入 P1 的 store 治理和大文件拆分

---

## 10. 最终建议

本轮最合理的策略不是“大重构”，而是：

- 先做 **4 个 P0 收口任务**
- 再补 **对应测试**
- 最后再做 **P1 结构治理**

这样做的好处是：

- 能最快降低真实业务风险
- 不会把当前可运行的业务链路打散
- 后续继续扩展支付、优惠券、社区功能时，维护成本会明显更低
